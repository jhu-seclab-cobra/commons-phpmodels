# PHP Models — Set Provenance Concept

Extends [concept.md](concept.md) with the one concern it does not cover:
where a document set's entries come from, and how a consumer ranks two
sets that state the same subject. Document Set, Model, Vocabulary, and
Category Mapping are defined there and used here unchanged. The origin
color of a tainted value, which the format also calls a provenance, is a
different concept and is not touched here.

## 1. Context

**Problem Statement**
A consumer mounts sets from several producers: an extraction over upstream
stub sources, a hand-reviewed correction set, a third-party fragment. Two
sets can state the same subject and unit, and the consumer must decide
which statement wins. Deciding by mount order alone hides the reason in
the consumer's code and breaks when a new producer appears; the reason is
a property of the set — how its entries were verified — and belongs with
the set.

**System Role**
The set provenance is the fourth fixed document of the document-set
convention: one statement per set naming its producer and its verification
kind, decoded and validated by this library, and ranked by a precedence the
consumer supplies. The fold that applies the ranking stays with the consumer.

**Data Flow**
- **Inputs:** one provenance document per set root (producer, verification
  kind); the consumer's precedence over verification kinds.
- **Outputs:** the set provenance attached to the loaded set; a total order
  over verification kinds for the consumer's fold.
- **Connections:** producer writes the document → this library (decode,
  validate, attach) → consumer (rank sets, fold entries by precedence).

**Scope Boundaries**
- **Owned:** the provenance document's shape and file name, the closed set
  of verification kinds, the precedence type and its default order, and
  attaching the provenance to the loaded set.
- **Not Owned:** the fold that resolves two entries for one subject
  (consumer), the mount order (consumer), and any claim about individual
  entries — provenance is stated once per set, never per entry.

## 2. Concepts

**Conceptual Diagram**
```
set root ─┬─ provenance.yaml ── producer + verification ──► Set Provenance ─┐
          ├─ index.txt, vocabulary.yaml, policy.yaml, documents ──► entries  │
          │                                                                  ▼
consumer: precedence (manual > generated by default) ──► fold: higher verification wins,
                                                               equal → consumer's mount order
```

**Core Concepts**

- **Name:** Set Provenance
- **Definition:** The statement of where one document set's entries come
  from: a Producer and a Verification. It travels with the set as one
  value and applies to every entry the set lists, so a consumer never
  inspects entries to learn how they were made.
- **Scope:** one per set; absent when the root holds no provenance
  document, in which case the consumer's own default applies.
- **Relationships:** attached to the Document Set at load; read by the
  consumer's Precedence; unchanged by a Category Mapping.

- **Name:** Producer
- **Definition:** The identifier of the process or party that emitted the
  set: an extraction over a named upstream release, a review, a
  third-party publisher. It documents the source for a reader and names it
  in diagnostics; it never decides precedence.
- **Scope:** a free non-blank identifier chosen by the producer.
- **Relationships:** one part of the Set Provenance.

- **Name:** Verification
- **Definition:** The closed kind stating how the set's entries were
  checked: *generated* — emitted by a program from an upstream source and
  never reviewed entry by entry; *manual* — written or reviewed by hand,
  with the reason for each departure recorded beside the entry.
- **Scope:** the two kinds; a document naming any other kind fails the
  load.
- **Relationships:** one part of the Set Provenance; the domain of the
  Precedence.

- **Name:** Precedence
- **Definition:** The consumer's total order over Verification kinds,
  highest first. When two mounted sets state the same subject and unit,
  the entry from the set whose verification ranks higher wins regardless
  of mount order; equal ranks fall back to the consumer's mount order.
  The default order ranks manual above generated.
- **Scope:** one per consumer, over verification kinds only; the Producer
  is never ranked.
- **Relationships:** supplied by the consumer; reads the Set Provenance of
  each mounted set; applied by the consumer's fold.

## 3. Contracts & Flow

**Data Contracts**
- **With producers:** a producer states its provenance once, in the
  provenance document beside the manifest; the document is decoded with
  the same strictness as every other document, so a stray key or an
  unknown verification kind fails the load naming the set.
- **With consumers:** the loaded set carries its provenance or none; the
  consumer holds one Precedence and ranks sets with it. A set from a new
  producer needs no consumer change: its verification kind places it.

**Internal Processing Flow**
1. Read — open the provenance document under the root; absence yields no
   provenance, not a failure.
2. Decode — strict decode of the producer and the verification kind.
3. Attach — the provenance becomes part of the loaded set, before the
   manifest's documents are read.
4. Rank — the consumer compares two sets' verification kinds through its
   Precedence when their entries meet.

## 4. Scenarios

- **Typical:** the generated declaration set states `generated`; the
  reviewed value rules set states `manual`. Both state `strlen`'s value
  unit; the manual entry wins under the default precedence whichever set
  the consumer mounted first.
- **Boundary:** a set's provenance document spells `verification: reviewed`.
  The closed kind admits no guess; the load fails naming the set.
- **Interaction:** a consumer mounts a third-party generated set after its
  own manual set. The manual entries keep winning; among the two generated
  sets the consumer's mount order decides.
